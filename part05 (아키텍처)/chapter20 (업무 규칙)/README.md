# 20장 업무 규칙

업무 규칙은 사업적으로 수익을 얻거나 비용을 줄일 수 있는 규칙 또는 절차다.  
대출에 N%의 이자를 부과한다는 사실은 은행이 돈을 버는 업무 규칙이다.  
프로그램으로 계산하든, 사람이 직접 계산하든 아무 상관 없다.

이런 규칙은 사업 자체에 핵심적이다.  
핵심 업무 규칙은 보통 데이터를 요구한다.(대출 잔액, 이자율, 지급 일정 등)

이 둘은 본질적으로 결합되어 있기 때문에 객체의 대상이 되고, 핵심 업무 규칙과 핵심 업무 데이터를 결합한 객체를 엔티티라고 하겠다.

## 엔티티

엔티티는 컴퓨터 시스템 내부의 객체로서, 핵심 업무 데이터를 기반으로 동작하는 일련의 조그만 핵심 업무 규칙을 구체화한다.

```
+-----------------------------+
|           Loan              |
+-----------------------------+
| - principle : double        |
| - rate      : double        |
| - period    : int           |
+-----------------------------+
| + makePayment()             |
| + applyInterest()           |
| + chargeLateFee()           |
+-----------------------------+
```

엔티티는 도메인을 대표하는 핵심 데이터이자 규칙 집합이다.  
그래서 DB, UI, 프레임워크 등 외부 요소에 절대 의존해서는 안된다.

클래스의 형태가 아니더라도 핵심 규칙을 외부 기술로부터 독립적으로 묶어둔 모듈이면 엔티티이다.

## 유스케이스

하지만 모든 업무 규칙이 엔티티처럼 순수한 것은 아니다.

어떤 규칙들은 자동화된 시스템 안에서만 의미를 가진다.  
예를 들어 대출 신청 화면 -> 신용도 확인 -> 대출 견적 화면 이동 같은 규칙은 시스템의 흐름을 정의한다.

이런 종류의 규칙을 유스케이스라고 한다.  
유스케이스는 사용자가 어떤 입력을 주고, 어떤 출력을 보며, 그 출력을 만들기 위해 시스템이 어떤 단계를 거치는지를 기술한다.  
따라서 유스케이스는 핵심 업무 규칙과는 달리 애플리케이션에 특화된 업무 규칙을 표현한다.

```
# 신규 대출을 위한 신상정보 수집

- 입력: 이름, 주소, 생일, 운전면허 번호, 주민번호
- 출력: 사용자 확인을 위한 입력 정보 + 신용도

## 기본 과정
1. 이름을 받아서 검증
2. 주소, 생일, 운전면허 번호, 주민번호 검증
3. 신용도 조회
4. 신용도가 500보다 낮으면 거절
5. 높으면 Customer를 생성하고, Loan Estimation을 활성화
```

유스케이스는 엔티티 내부의 핵심 업무 규칙을 어떻게, 언제 호출할지 명시하는 규칙을 담는다. (Customer 엔티티를 참조한 것을 주목)

또 중요한 점은 입력, 출력 데이터만 명시되었을 뿐, 인터페이스는 기술하지 않는다.  
시스템이 사용자에게 어떻게 보이는지 설명하지 않는다.

엔티티는 자신을 제어하는 유스케이스에 대해 아무것도 모른다.  
엔티티는 고수준, 유스케이스는 저수준이다.  
유스케이스가 입력, 출력에 더 가깝게 위치하기 때문이다.  
엔티티는 수많은 다양한 애플리케이션에서 사용될 수 있도록 일반화된 것이다.

## 요청 및 응답 모델

제대로 된 유스케이스 객체라면 데이터를 사용자나 다른 컴포넌트와 주고 받는 방식에 대해서는 알 수 없어야 한다.

요청 및 응답 모델이 독립적이지 않다면, 그 모델에 의존하는 유스케이스도 결국 입출력 모델이 갖는 의존성에 간접적으로 결합되어 버린다.

## 결론

업무 규칙: 소프트웨어 시스템이 존재하는 이유, 핵심적인 기능.  
사용자 인터페이스나 DB 같은 저수준에 관심사에 오염되면 안된다.

업무 규칙은 시스템에서 가장 독립적이며 가장 많이 재사용할 수 있는 코드여야 한다.
