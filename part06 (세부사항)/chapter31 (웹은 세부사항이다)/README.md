# 31장 웹은 세부사항이다

우리는 모든 연산 능력을 중앙 서버에 두는 방식과 모든 연산 능력을 단말에 두는 방식 사이에서 꾾임없이 움직여 왔다.

## 끝없이 반복하는 추

### 1. 초기 컴퓨팅

    컴퓨터실 + 천공카드 시대
    입력은 천공카드로, 출력은 배치 방식. 사용자가 직접 컴퓨터를 만질 일은 거의 없음.

### 2. 중앙 집중형 메인프레임 시대

    똑똑한 그린 스크린 단말기(green screen terminal)
    단말기 자체는 어느 정도 기능 있음.
    메인프레임 하나에 여러 단말기가 연결되는 구조.

### 3. 미니컴퓨터 시대

    다수의 멍청한 단말기를 연결
    단말기는 단순 입출력 장치에 불과하고, 모든 계산은 중앙의 미니컴퓨터가 수행.
    효율적이지만 중앙 장애에 취약.

### 4. 클라이언트–서버 아키텍처

    PC가 보급되면서 클라이언트가 일부 작업을 직접 수행.

    서버는 데이터 저장과 핵심 처리, 클라이언트는 UI·비즈니스 로직 일부 담당.

### 5. 웹 초창기

    멍청한 브라우저 + 서버 팜(server farm)
    브라우저는 단순 렌더러에 불과했고, 대부분의 로직은 서버에서 수행.
    서버는 HTML을 생성해서 내려주는 구조(정적 + CGI 기반).

### 6. 클라이언트 강화를 시도 — 애플릿(ActiveX·Java Applet)

    애플릿이 달린 똑똑한 브라우저
    브라우저 안에서 프로그램을 직접 실행하려는 시기.
    하지만 보안·호환·성능 문제로 실패.

### 7. 동적 페이지가 다시 서버 중심으로

    JSP / PHP / ASP 같은 서버 사이드 렌더링(SSR) 중심.

    브라우저 로직은 최소화, 서버가 HTML을 계속 새로 만들어 전달.

### 8. Ajax 혁명과 JavaScript 부상

    Ajax + JavaScript 등장으로 많은 처리가 브라우저(클라이언트)로 이동

    화면 일부만 갱신 가능

    UI/UX의 대폭 향상

    브라우저는 다시 “점점 똑똑해진 클라이언트”가 됨.
    (SPA 시대의 시작)

### 9. Node.js 등장

    서버로 JavaScript가 (또) 돌아옴

    프론트와 백을 하나의 언어로 통합 가능

    서버도 JS, 클라이언트도 JS

연산 능력을 중앙에 집중하는 방식과 분산하는 방식 사이에서 우리는 끊임없이 움직인다.

아키텍트로서 우리는 멀리 내다봐야 한다. 

## 요약

GUI는 세부사항이다. 웹은 GUI다. 따라서 웹은 세부사항이다.

GUI는 너무 특이하고 다채롭기 때문에 장치 독립적인 아키텍처를 추구하는 일이 터무니없다고 말할 수도 있다.  
이 주장이 어느 정도는 엃다.

하지만 UI와 애플리케이션 사이에는 추상화가 가능한 또 다른 경계가 존재한다.

UI에서 필요한 입력 데이터를 모으면 유스케이스에 입력으로 넘길 수 있고, 유스케이스는 처리 후 결과 데이터를 UI에 돌려주면 된다.

이렇게 하면 유스케이스는 UI를 장치 독립적인 추상화된 IO 장치처럼 다룰 수 있게 된다.

## 결론

이러한 종류의 추상화는 만들기 쉽지 않고 제대로 만들려면 수차례의 반복 과정을 거처야 할 것이다.  
하지만 가능하다.
